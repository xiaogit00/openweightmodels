## 1. Runtime topology

- **Web**: Next.js App Router, TypeScript, Node runtime for API routes and SSE.
- **Worker**: separate BullMQ consumer, same TypeScript workspace (`apps/worker`).
- **Postgres**: canonical state for every Comparison, Job, Run, Annotation, Discussion and Vote.
- **Redis**: BullMQ transport and SSE pub/sub only; never a source of truth.
- **Local**: Docker Compose (web, worker, Postgres, Redis, Mailpit). Homebrew Postgres/Redis is also supported.
- **Production**: AWS ECS Fargate (web + worker), ALB, RDS Postgres, node-based ElastiCache Redis, SES, ECR, Secrets Manager, CloudWatch, CDK TypeScript (ADR 0006).
- **Realtime**: SSE with Redis pub/sub and Postgres replay; no WebSockets.
- **Generation**: provider-agnostic OpenAI-compatible adapter. `MockProvider` is the default in development; OpenRouter is the first real adapter.
- **Auth**: Better Auth email magic link, SES in production and Mailpit locally (ADR 0005). Milestone 1 uses a seeded dev identity behind the same `getCurrentUser()` seam.

## 3. Invariants and state machines

### Comparison lifecycle

```
scheduled job → generating ──all Runs done/skipped──→ ready ──publish──→ published
                    │                                      ↑              │
                    └──────────── failure remains ─────────┘              │
                                                                           │
                                                        unpublish ─────────┘
```

- `draft` is reserved for future explicit draft support; M1 creates `generating` directly.
- `published` Comparisons can gain Challengers without leaving `published`.
- A failed Run blocks `ready` until it is retried, skipped, or auto-skipped after **24 hours**.
- Publish requires at least one `done` Challenger. A base-only Comparison cannot be published.
- Unpublish sets `status = 'ready'` and `published_at = NULL`; it stays readable by the Author.
- Soft delete hides it from everyone.

### Run lifecycle

```
queued → calling → streaming → done
   │         │          │
   └─────────┴──────────┴──→ failed ──retry──→ queued
                                └──skip──→ skipped
```

- A retry increments `attempt` and reuses the same Response row.
- `skip` is allowed only from `failed` or `queued`; it sets `skipped` and finalises the Job.
- Retry and Skip emit a `response.status` Job event (`queued` / `skipped`) so open Job pages update in place; the worker's next `calling` event follows normally.
- A 24-hour delayed BullMQ job (the default; `AUTO_SKIP_DELAY_MS`) auto-skips a Run that is still `failed`. The timer is scoped to the attempt, so a retry gets a fresh window.
- A Job is `ready` when every Run belonging to it is `done` or `skipped`.

### Add-model behaviour

- Maximum **4 challengers per Comparison**, including creation-time challengers.
- The Base model cannot be added as a Challenger; an existing model cannot be added twice.
- On a published Comparison, a newly added Challenger is visible to the **Author only** while generating; the public sees the tab when it completes. It is published atomically on completion, with no second review.
- A failed add is an author-only error tab with Retry/Dismiss; the public never sees it.

### Comparisons

| Method | Path | Notes |
|---|---|---|
| `GET` | `/comparisons` | published, non-deleted only |
| `GET` | `/comparisons/:id` | published public; draft author-only; otherwise `404` |
| `POST` | `/comparisons` | multipart upload; creates comparison + base response + job; returns `{ id, jobId, title }` |
| `PATCH` | `/comparisons/:id` | author; title/categories/effort only |
| `DELETE` | `/comparisons/:id` | author; soft delete |
| `POST` | `/comparisons/:id/publish` | author; requires ≥1 done challenger; returns `{ card }` |

| `POST` | `/comparisons/:id/responses` | author; `{ modelId }`; adds a Challenger and Job |

List query parameters: `cat`, `models` (comma-separated slugs), `effort`, `q`, `sort=live|top|new`, `cursor`, `limit` (default 48, max 100).

Response:

```json
{ "items": [ComparisonCard], "total": 123, "nextCursor": "opaque-or-null" }
```

Ordering:

- `live`: `published_at DESC, id DESC`
- `new`: `created_at DESC, id DESC`
- `top`: `(comment_count + 2 * annotation_count) DESC, published_at DESC, id DESC`

Cursors are opaque base64url JSON containing the sort, ID, score and timestamps.

`POST /comparisons` multipart fields:

- `file` — required, `.md`/`.markdown`/`.txt`, ≤1 MB, valid UTF-8
- `base_model_id` — required, enabled model
- `prompt` — required after front-matter fallback, ≤10,000 chars
- `model_ids` / `model_ids[]` — 1–4 enabled challengers, unique, excludes the base
- `title` — required after filename fallback, ≤200 chars
- `categories` — zero or more values from the fixed Category list
- `effort` — 1, 2 or 3

## 5. Job pipeline

1. **Schedule.** `POST /comparisons` validates the upload and quota, writes the Comparison (`generating`), Base Response (`done`), Job (`scheduled`) and one queued Response per Challenger in one transaction. It then enqueues **one BullMQ job per Run** and logs `job.scheduled`.
2. **Resolve.** The model registry row is loaded at write time. Disabled or unknown models are rejected before a Job exists; an unknown model at run time is marked `failed`.
3. **Run.** Each worker claims the Response with an atomic `queued → calling` update (a duplicate delivery then no-ops), sets the Job to `running`, and calls the provider with:
   - a single user message containing the Prompt,
   - `temperature: 0.7`,
   - `max_tokens: 4096`,
   - `stream: true`,
   - a 120-second timeout.
4. **Stream.** The worker appends chunks, updates `tokens` and `response.status` at most every 500 ms, and emits `response.status` job events.
5. **Finish.** On success it stores `content_md`, final tokens, latency and provider cost, sets `done`, then attempts to finalise the Job. On failure it stores the error, sets `failed`, schedules the attempt-scoped 24-hour auto-skip, then attempts to finalise.
6. **Finalise.** `finalizeJob` locks the Job row, checks every Run; if all are `done`/`skipped`, it sets the Job `ready`, moves a `generating` Comparison to `ready`, inserts a `job.ready` notification for the Author, emits `job.ready`, and writes `run.finished` activity only if the Comparison is already published.
7. **Publish.** Explicit `POST /publish` sets `published_at`, `status = published`, and emits `comparison.published` with the full card payload.

**Redis loss**: Postgres is authoritative. Non-terminal Runs can be re-enqueued from Postgres; the SSE stream falls back to polling. Redis must run with `maxmemory-policy: noeviction`; ElastiCache Serverless is not supported for BullMQ.

## 6. Upload parsing

- Accept `.md`, `.markdown`, `.txt`, **1 MB** maximum.
- Reject null bytes, invalid UTF-8 and empty bodies.
- Front matter is optional. It must start and end with a `---` line. Parse with a core YAML schema and **`maxAliasCount: 0`**; no custom tags.
- Only `prompt:` and `model:` are read. Both must be strings if present. Other keys are ignored.
- `prompt` is 1–10,000 characters. The form may override the front-matter prompt, but a non-empty prompt is always required to schedule.
- The body after front matter becomes the Base `responses.content_md`.
- `title` falls back to the filename stem with separators replaced.
- The front-matter `model:` value is matched against an enabled registry slug or display name to preselect "Generated by". An unknown value is ignored and the form asks the author to choose. The form's `base_model_id` wins at scheduling time.

## 7. Annotation anchoring and rendering

Supported markdown subset on day one: paragraphs, headings, ordered/unordered lists, fenced code blocks, inline code, bold, italic and links. Blockquotes and horizontal rules render. Raw HTML is escaped and rendered as text; images render their alt text; tables are not enabled (GFM is not used).

Annotatable runs are leaf text nodes and fenced code blocks for which the raw markdown slice equals the decoded value. Consequences:

- Selecting across bold/italic/link boundaries is **not annotatable**.
- Text containing markdown escapes or entities where raw ≠ decoded is **not annotatable** rather than silently drifting.
- Indented code blocks render but are **not annotatable**; fenced code blocks are.
- An Annotation cannot cross a paragraph or block boundary.
- Overlaps are rejected; adjacent annotations are fine.
- Offsets are UTF-16 code units, matching JavaScript and browser Selection.
- When an Annotation is deleted, its highlight and thread disappear; votes on the soft-deleted target remain in the table but are not read.
- A deleted thread message is always tombstoned in v1; hard deletion of childless messages is not implemented.

## 8. Quotas, cost and abuse

- **10 Jobs per user per hour** (`JOBS_PER_HOUR`).
- **50 Runs per user per day** (`RUNS_PER_DAY`), counting Challenger Responses.
- **4 concurrent provider calls** globally (`PROVIDER_CONCURRENCY`), enforced by worker concurrency.
- **4 challengers per Comparison** (`MAX_CHALLENGERS`).
- Duplicate runs for the same model in one Comparison are rejected by a unique index.
- Generation parameters are identical across Challengers so comparisons are fair.
- `responses.cost_usd` stores provider-reported cost; not displayed in v1.
- Exceeding a quota returns `429 rate_limited`.
- Magic-link request rate limiting and per-IP abuse controls are **not yet specified**; see open questions.

---

## 9. Security and privacy

- Public read: Board, published Comparisons, Discussion, Annotations and the ticker.
- Authenticated write: create, annotate, comment, vote, publish.
- Drafts and Jobs are author-only and return `404` to everyone else.
- Email addresses are private; handles are the public identity.
- Raw HTML is never rendered as HTML.
- Uploads are size-, encoding- and YAML-restricted.
- API keys live in environment variables / Secrets Manager, never in `models.api_base`.
- Admin takedown and model enable/disable are minimal M2 surfaces; report/flag, suspension, account deletion and export are launch gates.

## 10. Local development

```bash
# One command: web, worker, Postgres, Redis and Mailpit
docker compose up --build

# Homebrew fallback (no Docker)
brew services start postgresql@17
brew services start redis
createdb openweightmodels
pnpm db:init          # migrate, then seed only when the database is empty
pnpm dev:web
pnpm dev:worker
```

`pnpm db:seed` still replaces content with the deterministic fixtures, and
`pnpm db:reset` drops the public schema. Data survives `docker compose down`;
only `docker compose down --volumes` (or `pnpm stack:reset`) deletes it.

Setup and migration commands are documented in `README.md` and `docs/IMPLEMENTATION-STATUS.md`.
