# 16: Abuse controls, spend caps and delivery pipeline

**What to build:** The production system has guardrails and a repeatable delivery path. Magic-link and API endpoints are rate-limited, provider spend has an absolute ceiling and alarms, operational failures are visible to a named owner, and deploys run through CI using short-lived AWS credentials rather than stored keys.

**Blocked by:** 13 — Deploy staging on AWS.

**Status:** ready-for-human

- [x] Magic-link requests are limited per email and per IP; verification attempts are rate-limited.
- [x] Write and generation APIs enforce per-user and per-IP limits and return 429 with retry guidance.
- [x] A configurable monthly spend cap and AWS budget alarms bound model and infrastructure cost; breaching the cap stops new generations safely.
- [x] CloudWatch alarms cover ALB 5xx, unhealthy ECS tasks, queue depth and job failure rate, with a named owner.
- [x] Application errors are reported to the chosen error tracker with enough context to diagnose a failed Run.
- [x] CI runs typecheck, tests and build, then deploys through AWS OIDC without long-lived access keys.
- [x] Migrations run automatically and safely during deployment, with a documented rollback path.

## Comments

- 2026-10-29 — Implemented and verified offline (typecheck, 483 tests, `next build`, 37 infra tests and `cdk synth`). **Rate limits.** `packages/core/src/rate-limit.ts` is a fixed-window counter with an atomic Redis Lua increment and an in-process fallback; identifiers are SHA-256 hashed so emails/IPs are not Redis keys. Better Auth uses it as `rateLimit.customStorage`, so the 5-per-60s magic-link bucket is shared across both web tasks, `/magic-link/verify` has a stricter 10-per-300s per-IP rule, and `sendMagicLink` adds a 3-per-15min per-email bucket before delivery. Every authenticated write calls `requireUser()`, which now enforces 60/min per user and 120/min per IP; Create Comparison, Add model and Retry add a 6/min per user and 12/min per IP Run bucket. The client IP is the right-most `X-Forwarded-For` entry, which the ALB appends, so a spoofed left-most value cannot mint a fresh bucket; Better Auth trusts private proxy peers for the same reason. 429s carry `Retry-After`, a `retryAfter` body field and a message naming the wait; a suspended or handleless account still gets its 403 first. **Spend.** `MONTHLY_SPEND_CAP_USD` (staging default 100) sums provider-reported `responses.cost_usd` over the UTC month. Create/Add model/Retry refuse with `429 spend_cap_reached` and `Retry-After` until the next month; `processRun` re-checks before every provider call so an already-queued Run fails without spending. `OwmStagingOps` adds a monthly AWS `COST` budget (default $200) at 80% actual and 100% forecasted, because OpenRouter spend is not on the AWS bill. **Alarms.** New `OwmStagingOps` stack: SNS topic with the required `OWM_ALARM_EMAIL` email subscription; alarms for ALB 5xx and target 5xx (application 500s are target 5xx), unhealthy web targets, zero running worker tasks, queue depth > 25 and a >20% Run failure rate (`failed / (failed + finished)`, so a total outage still alarms). Queue depth and job outcomes are JSON log lines from the worker turned into `OWM/Queue`/`OWM/Jobs` metrics by CloudWatch Logs metric filters, so the worker needs no CloudWatch SDK or IAM permission. **Errors.** `packages/core/src/error-reporting.ts` posts a Sentry-compatible envelope over `fetch` when `OWM_SENTRY_DSN` is set, and always writes a structured `error.report` line. Failed Runs include response, job, comparison, model, turn, attempt, tokens and latency; secrets, API keys and database passwords are redacted. **Delivery.** `.github/workflows/ci.yml` runs `pnpm db:bootstrap`, typecheck, tests and build against Postgres 17/Redis 7, then on `main` assumes the OIDC deploy role (QEMU + Buildx for the ARM64 images) and runs `pnpm deploy:staging`. `pnpm deploy:ci` creates `OwmStagingCi`: a GitHub OIDC provider (or imports one) and a role fenced to the repository, `main` and the `staging` environment. No access key exists in the repo or GitHub. **Migrations.** The existing migration task still runs from the new image before any service update and aborts the release on a non-zero exit; `docs/DEPLOYMENT.md` now records the forward-only migration rule and a four-step rollback drill.
