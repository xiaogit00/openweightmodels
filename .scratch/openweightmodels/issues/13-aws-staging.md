# 13: Deploy staging on AWS

**What to build:** A staging environment runs the real production topology on AWS: separate web and worker containers on ECS Fargate behind an ALB, RDS Postgres, node-based ElastiCache Redis, SES for magic links, ECR for images, Secrets Manager for credentials and CloudWatch for logs. Migrations run as a deployment task. The Board, SSE, scheduling, a real generation, publishing and annotations all work over HTTPS.

**Blocked by:** 05 — One-command local environment; 07 — Sign in with email magic links; 12 — Run real OpenRouter generations.

**Status:** done

- [x] A documented CDK deployment bootstraps a clean AWS account and creates the staging stack.
- [x] Web and worker run as separate ECS Fargate services with health checks and correct scaling minima.
- [x] The ALB idle timeout is raised and SSE survives more than five minutes without traffic; heartbeats are visible.
- [x] RDS PostgreSQL and node-based ElastiCache Redis (cluster mode off, `noeviction`) are provisioned; a migration task runs before the web service rolls.
- [x] Provider keys, database credentials and SES credentials live in Secrets Manager and are injected at runtime; nothing secret is in the repository or database. (SES uses the web task role instead of stored SMTP credentials, so there is no SES secret to rotate.)
- [x] SES sends a magic link to a verified address while the account is in the sandbox.
- [x] The staging URL supports Board, sign-in, upload, real generation, publish, Comparison and Annotation.
- [x] Logs, basic metrics and a monthly cost estimate are documented.

- 2026-10-27 — Magic-link sign-in failed with `AccessDeniedException: ... not authorized to perform 'ses:SendEmail' on resource 'arn:aws:ses:...:identity/thefuelstack@gmail.com'`. The identity in the error is the *recipient*, not the sender: SES authorises `SendEmail` against every identity in the request, and in the sandbox each recipient is a verified identity in the account. `sesIdentity.grantSendEmail()` only granted the sending domain (`identity/staging.openweightmodels.net`), so the recipient identity was denied. The web task role now grants `ses:SendEmail`/`ses:SendRawEmail` on `identity/*` in the account/region, with a comment to narrow it to the sending domain after production access. Added a regression test asserting the web role's SES resources cover all identities. Foundation redeployed in place (no new task-definition revision, services stayed 2/2 and 1/1). Note for future debugging: `iam simulate-principal-policy` is unusable for SES in this account — it reports `explicitDeny` for `ses:GetAccount` and `ses:ListEmailIdentities`, which succeed live — so trust the API error, not the simulator.
