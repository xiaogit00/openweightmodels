# Backend spec — OpenWeightModels

This spec covers the data model, the API and the job pipeline. It is inferred from the designs; adjust it to fit the target stack.

## Data model (Postgres)
```
users(id, handle, avatar_url, created_at)

models(id, slug, display_name, monogram, provider, api_base, api_model_id,
       eta_seconds, enabled, created_at)
  -- the registry of hosted open-weight models available to compare against

comparisons(id, author_id, title, prompt, categories text[], effort smallint /*1-3*/,
            base_model_id, status /*draft|generating|ready|published|failed*/,
            created_at, published_at,
            comment_count int, annotation_count int)        -- denormalised for the board

responses(id, comparison_id, model_id, is_base bool,
          content_md text, tokens int, latency_ms int,
          status /*queued|calling|streaming|done|failed|skipped*/,
          error text, attempt int, created_at, finished_at)

annotations(id, response_id, author_id, kind /*bug|hallucination|good|question*/,
            start_offset int, end_offset int, quote text,  -- character offsets into responses.content_md
            votes int, created_at)
annotation_messages(id, annotation_id, author_id, body, created_at)

comments(id, comparison_id, author_id, parent_id null, about_model_id null,
         body, votes int, created_at)

votes(user_id, target_type /*comment|annotation*/, target_id, PRIMARY KEY(...))

jobs(id, comparison_id, status /*scheduled|resolving|running|ready|failed*/,
     created_at, started_at, finished_at)
```

## Upload parsing
- Accept `.md`, `.markdown` and `.txt`, up to 1 MB.
- Parse the YAML front-matter. Use `prompt:` (required if present) and the optional `model:`, which pre-selects "Generated by".
- The body after the front-matter becomes the base `responses.content_md`.

## API
```
GET  /api/comparisons?cat=&models=a,b&effort=&q=&sort=live|top|new&cursor=
GET  /api/comparisons/:id            -> comparison + responses + annotation summaries
POST /api/comparisons                -> multipart: file, base_model_id, prompt, model_ids[] (1-4), title, categories[], effort
                                        creates comparison(status=generating) + base response + job; returns {id, job_id}
POST /api/comparisons/:id/publish
POST /api/comparisons/:id/responses  -> {model_id}  ("Add model" on the comparison page; enqueues one run)
POST /api/responses/:id/retry
POST /api/responses/:id/skip

GET  /api/comparisons/:id/annotations
POST /api/annotations                -> {response_id, kind, start_offset, end_offset, body?}
POST /api/annotations/:id/messages   -> {body}
POST /api/comments                   -> {comparison_id, parent_id?, about_model_id?, body}
POST /api/votes                      -> {target_type, target_id}   (toggle)

GET  /api/models                     -> enabled registry for pickers
```

## Realtime
- `GET /api/stream/board` (SSE or WebSocket) emits:
  - `comparison.published` with the card payload. The board inserts it, or queues it when sorted by Top/New.
  - `activity` events for the ticker: compared, annotated, replied, finished.
- `GET /api/stream/jobs/:id` emits `response.status {model_id, status, tokens, latency_ms, error}` as runs progress, and `job.ready`.

## Job pipeline
1. **Schedule.** `POST /api/comparisons` writes the rows, then enqueues `job:{id}`.
2. **Resolve models.** For each selected model, load its registry entry (endpoint, model id, auth). Mark any model that is disabled or unknown as `failed`.
3. **Run in parallel**, one task per model:
   - Call the model's hosted API. Assume an OpenAI-compatible `/chat/completions` endpoint with `stream: true`, a single user message containing the prompt, and fixed generation params (temperature 0.7, max_tokens 4096) recorded on the job.
   - Stream tokens. Update the token count about every 500ms and publish to the job stream.
   - On completion, save `content_md`, `tokens` and `latency_ms`, and set the status to `done`.
   - On timeout or error, set the status to `failed` and store the error. The user can **Retry**, which re-enqueues with `attempt+1`, or **Skip**.
   - Use a per-call timeout of 120s.
4. **Ready.** When every run is `done` or `skipped`, set the job to `ready` and the comparison to `ready`, then notify the author.
5. **Publish.** This happens on an explicit "Publish to board". Set `published_at` and broadcast `comparison.published`.

Rate-limit job creation per user (e.g. 10/hour) and cap concurrent runs per provider.

## Annotation anchoring
- Store offsets against the **raw markdown** of the response, which is immutable once `done`.
- When rendering, map the offsets onto the rendered text nodes.
- Reject ranges that overlap an existing annotation. Alternatively, support overlaps by nesting the highlight spans.
